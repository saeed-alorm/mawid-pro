## Server and native contract

- Register at POST /v1/workspaces/:workspace/locations/:location/notifications/registrations with installation_id (UUID), application_id, environment, locale and token. com.mawid.customer.platinum is for current customer-only identities; com.mawid.management is for explicit current staff grants. Identifiers, tokens and client metadata never grant permissions. Local compatibility retains com.mawid.demo; hosted staging excludes it through its required server application/workspace/location allowlist.
- DELETE registrations/:installation?application_id=...&environment=... revokes only the current actor, scope and verified session. No-query legacy revocation affects only the development demo application. Rotation preserves the destination ID and increments the destination version. Delayed invalid-token and revoked-session results cannot clear a refreshed version.
- Signed registrations retain trusted issuer, subject, session ID and binding version. Dispatch rechecks current provider session, binding, membership/customer/professional access, package, environment and visit revision. A known revoked session clears destination ciphertext; a reader outage fails closed and retries. A native logout should deregister before provider logout; offline deregistration cannot keep a revoked provider session dispatchable.
- Opening GET inbox?contract=2 then POST inbox/:notification/open?contract=2 returns the current authorized visit, plus notification_kind and notification_id. The returned kind selects the native review flow. Review invitations reject changed/cancelled visits and revoked ownership. Booking alerts open current saved state. Review submission still uses the existing signed visit review endpoint and its current eligibility check.
- The 15-opening-minute reminder targets both current partners through management destinations. Review invitations target only the currently verified customer through customer destinations, two minutes after the final scheduled end. Revoked, stale and inappropriate destinations are suppressed. Lock-screen copy remains generic EN/AR. FCM data adds opaque application_id, workspace_id and location_id to existing routing IDs; restrictedPackageName and replacement tags remain explicit. Provider acceptance is not device receipt.
- GET /v1/session?workspace_id=UUID&location_id=UUID returns actor_id, workspace_id, location_id, roles and customer_ids after current server authorization. There is no identity binding or staff enrollment HTTP route.
- Authorized partner visit-core/view customer entries add late_cancellation_count and late_cancellation_flagged (four qualifying cancellations). The existing rolling 90-day, strict less-than-60-minute SQL policy supplies the count. Customers and employees do not receive these fields. The flag does not ban anyone.

## Hosted adapter and reviewed configuration

The separate scripts/database/hosted/worker.mjs adapter uses the same shared booking/notification services and mandatory VerifiedDataService. Local classes retain exact loopback/fixture restrictions. The adapter preserves the existing local #5 staging approach: pinned Supabase issuer/JWKS, at most eight operator-allowlisted fictional Auth subjects, separate restricted session/actor logins and verified Supabase session-pooler TLS. This preserves the approved direct-pooler boundary; it does not select an additional database proxy.

The session reader uses mawid_core.staging_auth_session(), copied from the existing reviewed staging permission adapter. The selected one-session SECURITY DEFINER function has a fixed pg_catalog search path, fully qualified sources, no PUBLIC execution and explicit current issuer/subject/session/binding filters. Supabase-managed Auth grants/policies are unchanged. The real disposable Supabase Auth suite exercises this exact SQL function. All reader transactions explicitly use READ ONLY.

supabase/hosted/staging-grants.review.sql is a review artifact, outside the fixture migration manifest. It preserves that Auth function boundary and specifies separate dormant booking/notification roles. Existing actor/session role collisions, function owner, RLS, privileges and actual login custody require operator review. The actor write-mode change remains commented and must be separately authorized. No automatic customer-profile matching, staff invitations, recovery override or synthetic verified bypass was introduced.

The Worker uses request-owned database pools and AsyncLocalStorage to route its shared HTTP bridge. Cloudflare documents [httpServerHandler](https://developers.cloudflare.com/workers/runtime-apis/nodejs/http/) and [pg compatibility](https://developers.cloudflare.com/hyperdrive/examples/connect-to-postgres/postgres-drivers-and-libraries/node-postgres/). The example config preserves nodejs_compat and enables Node HTTP server support. The original assets-only staging config and Pages behavior are unchanged.
