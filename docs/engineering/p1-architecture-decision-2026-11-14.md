Booking-event push is required in P1, with saved authoritative state, visible failures and retries; no push vendor selected. Staff individual accounts remain intended, setup deferred. This supersedes the earlier provider/framework shortlist as a current choice; those analyses remain history.

**Approved booking rules:** pending reserves no capacity; staff choose which competing request to confirm. Fifteen **opening-time** minutes is a response target, never automatic request expiry. Pause the clock at closing, resume remaining minutes at reopening, and keep already-overdue requests overdue. Accept future requests while closed, disclose review at opening, and start their response clock then. An offer holds a concrete new slot for 60 **elapsed** minutes across closing, capped only by the proposed appointment start; the customer may accept after closing without staff intervention. Admins confirm/propose/record walk-ins; managers assign Any and configure employee services/durations/schedules/breaks/absences; explicitly assigned roles may combine. Self-cancellation is allowed through exactly start minus 30 minutes. Count customer cancellations of confirmed appointments once per booking per salon over rolling 90 days; exclude pending withdrawals, expired offers, salon cancellations and duplicate retries. The fourth qualifying event flags history to authorized management; staff decide future requests, with no automatic ban.

**Other approvals:** live-pilot planning range US$20–40/month, aim toward $20 and evaluate the full bill against $40; this is not spending authorization. One-time expenses need actual prices and individual approval. Saeed owns technical issues, backups/restores and release approval; the pilot manager owns salon decisions/workflow feedback. Contact may occur at any time, without immediate-response/fix/SLA promise. Capacity is six days x 4–5h = 24–30h/week. Lebanon is the intended registration country; conditional willingness to register does not establish registration or approve a legal form/expense. Both customer add-to-calendar and staff Google Calendar visibility follow the **first pilot**; Calendly is excluded, MAWID stays authoritative, and two-way calendar edits are not approved. This defers external calendar integrations, not the management appointment calendar already in P1.

See the [dated approval ledger](p1-approved-decisions-2026-11-14.md) for source/precedence. ## Internal contract v1 — approved direction, technical defaults for review

Applies to customer Android, branded web, management Android and portal; not a public external Booking API. The architecture, roles and booking semantics above are approved. Wire-level defaults below are engineering design proposals, not a request to reselect the approved stack; record acceptance/refinements before dependent implementation.

| Area | Review contract |
|---|---|
| Identity and IDs | Opaque workspace/tenant, location, booking, service and professional IDs. Use workspace_id as the canonical tenant identifier; map historical tenant_id once at the boundary. Actor comes from the authenticated server session, never request bodies, demo PINs or brand manifests. Validate location/service/professional membership and object ownership on every operation, including exports. |
| Permissions | Customer can act on their own requests/offers/appointments. Admin can confirm/propose/decline and record walk-ins. Manager assigns Any and maintains staff eligibility/schedules. Permissions are explicit and additive; manager does not implicitly become admin. Admin and manager may be the same assigned person. Revocation affects server access, cached workspace data and notifications. No shared live admin credential. |
| Capacity | Pending and an Any assignment alone reserve nothing. At confirmation or offer creation, select a concrete eligible professional and reserve the entire service duration plus buffers, within hours/break/absence/location constraints. Scope non-overlap by workspace, professional and UTC interval [start,end). Offers reserve only the proposed new interval; original pending never holds an old slot. Rescheduling an already confirmed appointment is a separate later policy, not silently covered here. |
| Atomic transition | Authenticate/authorize; check expected_version and retry key; lock request and affected professional resources in stable order; evaluate offer deadlines and response-clock status after lock waits; expire relevant holds; check eligibility/capacity; commit booking, allocation, audit actor/event and outbox together. Bound lock/deadlock retries. No provider network call inside the transaction. Confirm-versus-confirm and accept-versus-expire have one authoritative outcome. |
| State | pending -> confirmed / proposed / declined / withdrawn; overdue is a separate warning, not a state transition or capacity reservation; proposed -> confirmed / declined / expired / withdrawn, releasing its hold on non-acceptance. confirmed -> cancelled within authorized rules. State labels and explanatory customer text must distinguish a request from a reservation. Past-start pending requests stay pending; block past-time confirmation and require staff to propose a future time (direct owner approval in this continuation). Walk-ins use the same authoritative capacity path. No automatic winner. |
| Time | Store UTC instants with location IANA zone Asia/Beirut; recurring coverage/service schedules remain local-wall-time rules. Nonexistent DST input fails validation; repeated wall time requires explicit offset. Compute service duration, offer expiry and cancellation cutoffs in elapsed time; compute the response target using actual opening intervals, closed days and holidays. Return server_time, response_due_at, overdue, offer_expires_at and version. Client clock and delayed cleanup jobs never decide availability. |
| Versions/retries | Contract version v1, per-booking monotonically increasing version and expected_version on mutations. Scope idempotency key to workspace+actor+operation; canonical payload hash and committed response saved atomically. Authorize before replay; identical retry returns recorded outcome, changed payload returns IDEMPOTENCY_CONFLICT. Proposed retention: 7 days, to approve alongside maximum offline retry policy. Never replay sensitive data to a revoked actor. |
| Errors | Validation 422; missing session 401; forbidden workspace/unknown object return uniform 404 without existence disclosure; authorized but disallowed action 403. Conflicts 409: SLOT_UNAVAILABLE, STALE_VERSION, IDEMPOTENCY_CONFLICT, OFFER_EXPIRED, CANCEL_CUTOFF. An overdue pending request is still actionable; do not return REQUEST_EXPIRED merely for missing the response target. Rate limit 429 with retry guidance; transient 503 with safe same-key retry. Include request correlation ID, stable code and safe message, never another customer's record. |
| Reads/updates | Workspace-scoped cursor pagination with proposed page limit 50; version/state returned on reads. On push, resume and reconnect, fetch authoritative state. Offline work remains visibly unconfirmed. EN/AR clients map the same codes and states; no local confirmation before commit. |
| Events/notifications | Minimal event: event_id, workspace_id, location_id, booking_id, version, type, actor_id, occurred_at. Outbox commit is atomic; delivery is asynchronous, deduplicated and visible on failure. Retry with bounded backoff and expiry; no notification failure rolls back booking. Bind destinations to environment/package/installation/user/workspace, reauthorize at dispatch/open; no sensitive lock-screen payloads. Channel selection and live identity proof remain approval gates. |

Synthetic routing examples remain the existing com.example.mawid.branda, com.example.mawid.brandb and com.example.mawid.management identities in [Android design](android-distribution.md). Actual package namespace, authorized assets, environment/config schema and stable-link mapping require private approval. Manifests route; they never authorize. A shared-source fix must rebuild both customer variants, alongside management compatibility.
